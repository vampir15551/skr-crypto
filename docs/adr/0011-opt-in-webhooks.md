# 0011 — Opt-in webhooks for audit-event delivery

## Status

Accepted. 2026-04-30. Introduced in 1.7.0.

## Context

Up to 1.6 the only way for a back-office to learn about a service-side
event (`SEND_SUCCESS`, `SEND_REJECTED`, `RECEIPT_RESOLVED`, ...) is to
poll. Audit-log tail, `/api/v1/tx/.../status` polling, /metrics
scraping. Polling is correct — and we still recommend it as the
**source of truth** — but it has a real operational gap:

- Each event-driven action on the back-office side waits a polling
  interval. Settlement workflows that key off `RECEIPT_RESOLVED
  status=OUT_OF_ENERGY` have to wait up to one tick (30-60s by
  default) to react.
- Multiple back-offices polling the same audit file scale linearly
  with N callers. Modest, but it's still N-callers ⨯ scrape-rate
  load.

Webhooks are the natural answer. We rejected them in 1.0 ([explicit
non-goal](../architecture.md#what-this-codebase-deliberately-does-not-do))
because they couple the service to a delivery-guarantee surface that
historically becomes a tar pit (retries, backoff, dead-letter queues,
clock skew, signing schemes). 1.7 reconsiders this with a **bounded**
design that keeps the audit log as the source of truth and treats
the webhook stream as a strictly best-effort secondary channel.

## Decision

Add an **opt-in** webhook delivery layer with the following bounds:

1. **The audit log is still the source of truth.** Webhooks are a
   secondary notification channel. A failed webhook delivery does
   NOT roll back the on-chain transfer or modify any other state.
2. **Opt-in via env.** `WEBHOOK_URLS` is a comma-separated list of
   target URLs. Empty = feature disabled. There is no UI / runtime
   way to enable webhooks; it requires a config change + restart,
   like every other money-adjacent setting.
3. **HMAC-signed payloads.** Each delivery carries an
   `X-SKR-Signature` header containing
   `t=<timestamp>,v1=<hex-hmac-sha256(timestamp.body)>`.
   The HMAC key is `WEBHOOK_SIGNING_SECRET` (32+ random bytes,
   generated by `skr-crypto webhook setup`). The receiver verifies
   both the signature AND that `now - t < tolerance` (default 5min)
   to defeat replay.
4. **Persistent delivery state in SQLite.** A `webhook_deliveries`
   table keyed `(id, audit_event_id, url)` records every attempt:
   status (pending / delivered / failed / giving_up), attempts,
   last_response_at, last_response_code, last_error.
5. **Bounded retry policy.** Exponential backoff with cap. Default:
   5 attempts at 0s, 30s, 2m, 10m, 1h. After the last failure, the
   delivery is `giving_up` — written to audit as a
   `WEBHOOK_GIVEUP` event so operators get a signal.
6. **Subset of events.** By default only `SEND_*` and `RECEIPT_*`
   events are delivered. `STARTUP_CHECK` / internal events are not
   surfaced (configurable via `WEBHOOK_EVENTS=...`).
7. **Background worker thread.** Delivery happens off the request
   path. /send returns 200 the moment audit fsync lands; the webhook
   delivery is queued for the worker. The hot path is never blocked
   by a slow webhook receiver.

Schema:

```sql
CREATE TABLE webhook_deliveries (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    audit_event_id  TEXT NOT NULL,        -- audit record id
    url             TEXT NOT NULL,
    payload         TEXT NOT NULL,        -- JSON, exactly what we POST
    status          TEXT NOT NULL,        -- pending|delivered|failed|giving_up
    attempts        INTEGER NOT NULL DEFAULT 0,
    next_attempt_at REAL NOT NULL,
    last_response_at REAL,
    last_response_code INTEGER,
    last_error      TEXT,
    created_at      REAL NOT NULL
);
CREATE INDEX idx_wh_status_next ON webhook_deliveries(status, next_attempt_at);
```

Wire format:

```http
POST /your-webhook-endpoint HTTP/1.1
Content-Type: application/json
X-SKR-Signature: t=1730294400,v1=a1b2c3d4...
X-SKR-Event: SEND_SUCCESS
X-SKR-Delivery-Id: 12345

{
  "id": "676dde64-9",
  "event": "SEND_SUCCESS",
  "timestamp": "2026-04-30T07:42:59.748789+00:00",
  "wallet": "cold",
  "from_address": "TColdxxx...",
  "to_address": "TRX9SbJ...",
  "amount": "245.50",
  "txid": "abc123",
  "idempotency_key": "invoice-741",
  "client_ip": "10.0.0.42",
  "token_id": "8d7e6b1234ab",
  "result": "broadcast",
  "details": "elapsed=1.43s risk=low"
}
```

Receiver verification (5 lines of any language):

```python
import hmac, hashlib, time
def verify(secret, header, body):
    parts = dict(p.split("=") for p in header.split(","))
    t, sig = parts["t"], parts["v1"]
    if abs(time.time() - int(t)) > 300: return False
    expected = hmac.new(secret.encode(), f"{t}.{body}".encode(),
                        hashlib.sha256).hexdigest()
    return hmac.compare_digest(sig, expected)
```

CLI surface:

```text
skr-crypto webhook setup            # generate signing secret + .env entry
skr-crypto webhook test <url>       # POST a synthetic event (verify wiring)
skr-crypto webhook list-deliveries  # tabular view of recent attempts
skr-crypto webhook retry <id>       # force-retry a giving_up delivery
```

Metrics:

- `skr_crypto_webhook_attempts_total{result="success|fail"}`
- `skr_crypto_webhook_giveup_total`
- `skr_crypto_webhook_queue_depth` — gauge

## Consequences

**Operators get near-real-time event delivery without polling.**
Typical delivery time: <2s after audit fsync. The 30-60s polling
gap closes for callers that integrate with webhooks.

**The audit log remains the source of truth.** Webhook delivery
failures don't roll back anything. A receiver that's down for a
day comes back, finds the events in the audit log, and reconciles.
The webhook stream is a **convenience**, not a contract.

**Security: HMAC + timestamp prevents replay** of an intercepted
delivery. The receiver MUST verify both, and we document this
prominently. We don't ship a Python `verify_webhook` helper because
inter-language receivers (Node.js, Go, Ruby, ...) are common —
better to publish the spec.

**Bounded blast radius.** A misbehaving webhook receiver only fills
the `webhook_deliveries` table; it cannot block /send or /balance.
The retry policy gives up after 5 attempts, so a permanently-broken
receiver stops generating background load within ~1 hour.

**Cost: one daemon thread + N HTTP attempts per audit event** where
N is the number of `WEBHOOK_URLS`. For an operator with 1 URL and
1 transfer/sec sustained, that's ~1 outbound HTTP/sec — negligible.

**Wire-format additions:** none on the existing /api/v1 endpoints.
The only new API is `GET /api/v1/webhook/deliveries` (operator-only,
admin scope) and the webhook payload itself, which is the same shape
as audit records.

## Alternatives considered

- **Block /send until webhook delivery succeeds.** Couples caller
  latency to receiver latency. The whole point of being async-on-
  delivery is to keep /send fast. Rejected.
- **Use a pub/sub system (RabbitMQ, Redis Streams, NATS).** Better
  scaling story; massively more deployment surface. Rejected — we
  don't have any infrastructure dependency and don't want to add
  one for ~1 outbound HTTP/sec.
- **Send the entire audit record verbatim, including
  `client_ip`/`token_id` etc.** Some receivers might prefer a
  redacted shape. We send everything by design — operators who care
  about which fields go to which receiver should run their own
  proxy. Keeping the wire format = audit format makes the spec
  trivial.
- **Make webhooks "exactly-once."** Impossible without two-phase
  commit on the receiver. We're "at-least-once with bounded retries
  + dedup-via-`X-SKR-Delivery-Id`". Receivers MUST be idempotent.
- **Allow per-event-type filtering on the wire.** YAGNI. Default
  `WEBHOOK_EVENTS=SEND_*,RECEIPT_*` is enough; operators with weird
  needs can run their own filter on top.
- **PGP-sign instead of HMAC.** Wider receiver complexity; HMAC is
  the industry-standard for service-to-service webhooks (Stripe,
  GitHub, Twilio). Stick with HMAC.
